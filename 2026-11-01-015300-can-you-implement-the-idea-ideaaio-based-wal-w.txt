  default stays sync, which leaves the old path unchanged. All the checks below
  passed, including the crash tests: every commit the server acknowledged
  survived. One limit: the crash tests kill processes but can't cut power, so
  the "completed means durable" part rests on O_DSYNC rather than being tested
  directly. On this laptop's drive it matches the old path at low concurrency
  and is up to 31% faster at 128 clients. The changes are uncommitted in your
  working tree (13 files).

  How it works

  The core is in xlog.c (src/backend/access/transam/xlog.c#L2788):
  - Durable writes: in AIO mode, WAL files are opened with O_DSYNC, or
    O_DIRECT|O_DSYNC if debug_io_direct=wal. A finished write is already on
    disk, so no separate fdatasync is needed.
  - Starting writes: XLogAioIssue (src/backend/access/transam/xlog.c#L3322) runs
    under WALWriteLock, starts the write and returns without waiting. It
    records each write in a small shared list ordered by LSN.
  - The core rule: when a write finishes, XLogAioAdvanceLocked
    (src/backend/access/transam/xlog.c#L2912) moves the "durable up to" pointer
    only to the end of the unbroken run of finished writes, as the doc's "core
    rule" requires.
  - No buffer reuse during a write: the "written up to" pointer also only moves
    when writes finish, so a WAL buffer can't be reused while the disk is still
    reading it.
  - Waiting: XLogFlushAio (src/backend/access/transam/xlog.c#L3578) does no I/O
    itself. It waits on the oldest write still in flight.
  - Same page, two writes: two writes covering the same bytes of a WAL page are
    never in flight together. The first write to reach a page also writes zeros
    over the rest of it, as today's code does. With buffered I/O, later small
    commits on that page are disjoint byte ranges and can go in parallel.
  - Other cases handled:
    - writes are split at segment boundaries
    - archiving notifications are sent only once a whole segment is durable
    - short writes are finished synchronously
    - failures PANIC, as today
    - if no AIO handle is available, the write is done synchronously
    - IO workers reopen the WAL file themselves
  - New settings: wal_io_method (sync / aio) and wal_io_max_inflight (default 1,
    max 64), both documented in config.sgml.

  Bugs testing found, and the fixes

  1. Wait before submit: another backend could start waiting on a write before
     it was submitted, which would PANIC. Now a write only becomes visible to
     waiters after it is submitted.
  2. Postmaster death mid-commit: if the postmaster died while a backend was
     waiting for its WAL inside a commit, the backend ran its exit cleanup and
     tried to abort a commit already recorded in WAL. In waiteventset.c
     (src/backend/storage/ipc/waiteventset.c#L251), a backend in that state now
     keeps waiting until its write finishes. If nothing finishes within 30
     seconds, it exits immediately, which looks like a crash to recovery. In
     method_worker.c (src/backend/storage/aio/method_worker.c#L499), IO workers
     now finish their queue before exiting, and once the postmaster is dead new
     I/O runs synchronously. Exiting immediately without the 30-second wait was
     not enough: backends waiting on locks hung forever.
  3. Stale WAL after a crash: writing only the new bytes could leave old WAL
     from before a crash right after the new end of WAL. Recovery might have
     replayed it. That is why the first write to each page zeros the rest of it.
