# AIO WAL writes: test results and scripts

Measurements and correctness tests for the `wal_io_method = aio` prototype
(see `../AIO-based WAL Writes in PostgreSQL Today vs. Proposed.md`), taken on
2026-11-01 on a laptop: 12 cores, WDC PC SN530 512 GB NVMe, ext4, Linux 7.0.

## Code versions

The implementation changed during testing, so every row is tagged with the
version it ran on. Only compare rows from the same `code_version` unless the
point is to show the effect of a change.

| version | what changed |
|---|---|
| `v1` | First version. Whole-page writes; a write starting in the middle of a page waits for the previous write. |
| `v2` | Exact byte-range writes with no same-page waits. **Unsafe** (could leave stale WAL after the end of WAL) and superseded. Kept only to show why pipelining small writes didn't help. |
| `v3` | v2 plus the "zeroing write" rule: the first write reaching a page also zeroes the rest of it. The in-flight cap and zeroing waits happen before taking WALWriteLock. Default `wal_io_max_inflight` changed to 1. |
| `v4-step1`, `v4-step2` | Intermediate steps towards v4: single "reaper" waiter, then 32 MB maximum write size. |
| `v4` | v3 plus single reaper waiter, no waiting while holding WALWriteLock, 32 MB maximum write. |
| `v5` | v4 plus an fsync operation in the AIO subsystem. With `wal_sync_method = fdatasync` (Linux default) or `fsync`, WAL is written to the page cache and the fsync is done via AIO; with `open_datasync`/`open_sync`, the `O_DSYNC` scheme of v4 is used. Also fixes IO workers dropping queued I/O after postmaster death. **The final code.** In `throughput_v5.csv`, AIO rows have `wal_sync_method` set: `fdatasync` = fsync scheme, `open_datasync` = `O_DSYNC` scheme. In older files, AIO rows always used `O_DSYNC`. |

## Results (`results/`)

All CSV files are generated by `results/build_csv.py`, which embeds the raw
tables as printed by the scripts. Rerun it after editing the raw data.

### `throughput.csv`: one row per (run, config, client count)

| column | meaning |
|---|---|
| `run` | which experiment the row belongs to; plot one `run` as one chart |
| `code_version` | see above |
| `storage`, `latency_ms`, `write_cache` | device: local NVMe, or the emulated disk (`dm-delay` adds `latency_ms` to every read, write and flush). `write through` models cloud block storage (no cache flushes) |
| `workload` | `pgbench -N scale 20` (small commits) or `large txn (big.sql)` (500 rows, about 150 kB of WAL per commit) |
| `stat` | single run or median of 3, and run length |
| `config` | label of the configuration |
| `wal_io_method`, `io_method`, `wal_io_max_inflight`, `direct_io`, `wal_sync_method` | the settings behind `config` (`direct_io` = `debug_io_direct = wal`) |
| `clients` | pgbench clients |
| `tps` | transactions per second |
| `latency_avg_ms` | only recorded for the `nvme_v1` / `nvme_v2` runs |

Runs:

| run | storage | workload | notes |
|---|---|---|---|
| `nvme_v1`, `nvme_v2` | local NVMe | pgbench -N | first versions, `wal_io_max_inflight = 16` |
| `nvme_v2_inflight_sweep`, `nvme_v3_inflight_sweep` | local NVMe | pgbench -N | effect of `wal_io_max_inflight` |
| `nvme_v3_final` | local NVMe | pgbench -N | median of 3; includes `O_DIRECT` variants |
| `dev1ms_writeback_v3` | 1 ms, write-back | pgbench -N | every `O_DSYNC` write also forces a cache flush |
| `dev{1,4}ms_writethrough_v3/_v4` | 1 / 4 ms, write-through | pgbench -N | cloud-disk model |
| `dev4ms_big_*`, `dev1ms_big_v4` | 4 / 1 ms, write-through | large txn | `dev4ms_big_v4_a` and `_b` are two runs of the same code (shows the run-to-run noise) |

Suggested charts: TPS vs clients per `run`, one line per `config`; or, for the
`*_inflight_sweep` runs, TPS vs `wal_io_max_inflight` per client count.

### `throughput_v5.csv`: v5 runs

Same columns as `throughput.csv`, written directly by `scripts/bench.sh`
(medians of 3 on NVMe, single runs on the emulated disk). Runs:
`dev4ms_writethrough_v5`, `dev4ms_big_v5`, `nvme_v5`, `nvme_big_v5`.
Concatenate it with `throughput.csv` to plot everything together.

### `crash_tests.csv`: crash and power-loss correctness

One row per test run: how many crashes or power cuts were done, how many
commits the server had acknowledged, and how many of those were missing after
recovery (always 0). The `fsync=off` row is the negative control showing that
the power-cut test does detect data loss. `results/raw/*.log` has the
per-crash lines of the latest run of each test that was still on disk.

### Other files

- `regression.csv`: regression/isolation suite results per version and setting.
- `steady_archive.csv`: archive completeness and `pg_waldump` check after a
  pgbench run, with the number of WAL writes seen in flight and of
  out-of-order completions that were correctly held back.
- `micro.csv`: `pg_test_fsync` on the NVMe, an aligned/unaligned 2 MB `O_DSYNC`
  write test, and WAL write counts and sizes in the large-transaction runs.
- `wait_events.csv`: `pg_stat_activity` wait-event samples (every 50 ms)
  during large-transaction runs, used to find bottlenecks.

## Test suite (`tests/`): correctness of the current code

Build with `-Dliburing=enabled`. Use `-Dcassert=true` (assertions) for these
tests; a release build is also worth running, since races depend on timing.
`run_all.py` runs every test for every configuration in `tests/modes.txt` and
appends one CSV row per (mode, test):

```sh
tests/run_all.py --inst INSTALLDIR --build BUILDDIR --work /tmp/aiotest \
                 --out results3/correctness.csv --label "laptop ext4 cassert"
tests/run_all.py ... --tests crash,repl --modes uring-ods-if16,worker-fds-if16
```

| test | what it checks |
|---|---|
| `regress` (`regress.py`) | PostgreSQL's regression and isolation suites (meson `running` setup) against a server writing WAL with AIO. Also run once with `wal_io_method = sync` (mode `stock`) as the baseline, so environment failures can't be mistaken for AIO failures. |
| `crash` (`crash.py`) | 16 clients commit small, large (40 rows), async and two-phase transactions; the server is crashed at a random moment, alternately SIGKILL of every process and of the postmaster only (children must exit on their own, with IO possibly in flight). After each recovery: every acknowledged commit present in full, `amcheck` (B-tree + heap) clean. Logs must have no PANIC or assertion failure. |
| `chaos` (`crash.py --chaos`) | The crash test while a thread reloads random values of `wal_io_max_inflight`, `wal_io_pipeline_threshold`, `wal_io_eager_issue`, `wal_io_inline_fsync` and `wal_sync_method` every 50-300 ms (changing `wal_sync_method` closes and reopens the WAL segment while IO may be in flight). |
| `repl` (`repl.py`) | Streaming standby + archiving. The primary is crashed under chaos load; the standby must never have received WAL beyond what the primary recovered (the walsender may only send WAL that is durable), must reconnect and end up with identical contents. The archive must have no gaps and `pg_waldump` must parse all of it. Then the standby is promoted (AIO WAL on a new timeline), crashed and recovered (acknowledged commits, amcheck). Finally single-user mode (where AIO is not used) with `wal_io_method = aio`. |
| power cut | `POWERCUT=1` turns `crash`/`chaos` into power-loss tests: the data directory must be on the `dev.sh` device (file -> loop -> dm-delay -> dm-flakey -> ext4), which drops every write from the cut on; the page cache is lost. Needs root (`sudo -v` first): `sudo -E tests/dev.sh setup 0 0`, then `POWERCUT=1 PGDATA_DIR=/tmp/pg-aio-testdisk/mnt/data tests/run_all.py ... --tests crash,chaos`. |

Modes (`tests/modes.txt`) cover both durability schemes (fsync: `fdatasync`,
`fsync`; O_DSYNC: `open_datasync`, `open_sync`), buffered and direct IO,
`io_method` `io_uring` / `worker` / `sync`, `wal_io_max_inflight` 1 and 16,
pipelining (`wal_io_pipeline_threshold = 0`) and the eager-issue / inline
switches. Each test can also be run on its own; see the usage line at the
top of each script.

## Benchmarks (`bench/`)

| file | purpose |
|---|---|
| `bench.sh` | Paired throughput benchmark: every config's server runs at the same time; pgbench alternates between them (5 s runs, order rotated each round), so changes in the device's speed hit all configs alike. Device canary gate before every block. `WORKLOAD=pgbench` (`pgbench -N`) or `big` (`big.sql`). |
| `analyze.py` | Each config vs the stock config of the same durability mode: per-round TPS ratio, median over rounds, min/max, rounds won; drops blocks where the device collapsed. Writes `paired.csv` and `tps.csv`. |
| `make_golden.sh` | The pgbench scale-20 cluster that `bench.sh` reflink-copies (no setup writes). |
| `cfg_default.txt` | Stock vs AIO in both durability modes. |
| `azure/` | Same benchmark on an Azure VM with a network disk: `pack.sh` (laptop) -> `vm_setup.sh` (VM) -> `run_azure.sh`. |

```sh
bench/make_golden.sh STOCK_INST /mnt/xfs/golden-s20
sed "s|INST|$HOME/pgaio/inst|" bench/cfg_default.txt > /tmp/cfg.txt
CLIENTS="1 4 16 64" ROUNDS=6 bench/bench.sh /tmp/cfg.txt raw.csv
bench/analyze.py /tmp/cfg.txt raw.csv
```

`tests/dev.sh` also provides the emulated slow disk for benchmarks
(`sudo -E tests/dev.sh setup 4 4; sudo -E tests/dev.sh writethrough`).

`results/` and `results2/` hold earlier campaigns; the scripts that produced
them (bench.sh v1, bench2.sh, crash_test.py, steady_test.sh, paired2.py, ...)
were replaced by the ones above.
